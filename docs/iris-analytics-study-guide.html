Iris Analytics · long-term data architecture

Raw facts stay true. Every dashboard view can be rebuilt.

Iris v2 keeps the operational simplicity of one SQLite database while separating registered sites, immutable event facts, and disposable analytical projections. This guide explains the invariants, failure boundaries, and the signals that justify a future database split.

01 · Mental model

It is still one database, but no longer one table.

Control plane

sites, site_domains, and reserved ingest_keys describe who may send data and how that data is interpreted.

Raw fact log

events is append-only application data. An accepted event is durable here before Iris returns 202.

Read models

Sessions and daily aggregates are derived. If their meaning changes or they become corrupt, clear them and replay raw events.

The governing invariant
An accepted event is durable in events. Projection lag may delay a dashboard update, but it never changes whether ingestion succeeded.

Why this is the long-term shape

The old single-table approach was attractive while every query was a small scan. It coupled ingestion, site discovery, identity semantics, and reporting to the same rows. V2 introduces explicit ownership and derivation boundaries without paying the deployment cost of Kafka, Redis, PostgreSQL, or ClickHouse. The logical boundary—not SQLite—is the valuable architecture.

Durable vs rebuildable

Raw events are backed up and retained deliberately. Projections are versioned caches of meaning.

Public vs secret

Site IDs and browser ingest identifiers are public. The admin bearer token is server-side only.

Occurrence vs receipt

Both client occurrence time and server receive time are stored as integer UTC microseconds.

Site-local vs UTC

Instants are UTC; calendar grouping and visitor rotation use the registered IANA timezone.

1 · SDK constructs the event

It creates a stable UUID event ID, records occurrence time, includes wire version v and SDK version sv, then resolves site-scoped visitor and session IDs.

2 · API validates meaning

The handler enforces method and size, decodes one event or a maximum of 50, requires stable identifiers, validates the registered site and hostname, normalizes URLs, and derives the site-local day.

3 · Serialized writer commits raw facts

The event receives monotonic seq. A duplicate id uses conflict-do-nothing, making retries safe. A batch is atomic.

4 · The client receives 202

202 means the raw SQLite transaction committed. It does not promise that the projector has caught up or that every downstream chart has refreshed.

5 · Projector advances atomically

Every 250 ms it reads at most 1,000 events after the checkpoint, updates daily sets/metrics and affected sessions, then advances the checkpoint in the same transaction.

6 · Reads choose the correct source

Eligible complete-day queries use projections. Exact, partial-day, or not-yet-projected answers may use raw events. /api/status exposes the gap.

Why not put everything in one JSON event table?

Raw JSON is flexible but poor at ownership constraints, uniqueness, referential integrity, stable filter performance, and explicit lifecycle policy. V2 keeps flexible custom properties in JSON while moving durable concepts—site, domain, occurrence, pathname, session, visitor, version—into typed columns.

Why not fully normalize custom properties?

An entity-attribute-value model turns every analytical filter into joins and loses useful type guarantees. Iris instead uses a hybrid rule: JSON for the long tail, typed columns and migrations for dimensions that become stable product concepts.

05 · Projection semantics

A checkpoint is only trustworthy when it commits with its derived writes.

Ordering

Raw seq, not occurrence time, defines replay order. Sessions touched in a batch are recomputed from their raw events through the batch’s final sequence, handling late occurrence times.

Atomicity

Derived updates and checkpoint advance share one transaction. A failed batch rolls back both, so retrying cannot double-count.

Versioning

A projection-version mismatch triggers a rebuild before HTTP serving. Projection-backed reads also verify the expected version.

Repair

iris-server rebuild-projections clears derived state only, resets the checkpoint, and replays the complete retained raw log.

Do not “fix” a chart by updating raw events. Correct projection logic, bump its version, rebuild, and verify. Delete raw facts only for explicit retention or privacy operations.

Projection lag formula

projection_lag = last_raw_seq - projection_last_seq

Lag above zero can be normal for roughly one polling interval. Persistently growing lag means the projector cannot keep pace or is failing. Raw durability remains intact, but projection freshness does not.

06 · Identity & time

Privacy and calendar semantics now share one site timezone.

Visitor

A browser-local random ID scoped to the site. It rotates at midnight in the registered IANA timezone. It is not a user or person identifier.

Session

A site-scoped ID in localStorage, shared by same-origin tabs, rolling after 30 minutes without tracked activity.

Local day

Derived from occurrence time at ingestion and stored on every event. Daily projections group by this stable value.

The SDK timezone must match the registered site. Once the first event exists, Iris rejects timezone changes: otherwise historical rows, future visitor rotation, and daily charts would silently use incompatible definitions.

Interpretation: a seven-day “visitors” query may count one active browser up to seven times because its visitor ID intentionally rotates daily. Session counts represent 30-minute inactivity windows as observed by this browser SDK, not authenticated people.
07 · SQLite runtime

One serialized writer, four readers, WAL between them.

Per-connection rules

foreign_keys=ON, WAL journal, five-second busy timeout, synchronous=NORMAL.

Writer ownership

Ingestion, site mutation, migration, projection, and retention all serialize through the writer.

Benefit

Readers can continue during commits and competing Go write connections no longer manufacture lock contention.

Limit

SQLite is still single-writer. Long retention deletes or migrations can delay ingestion; WAL growth and long readers need monitoring.

08 · Trust model

Registration adds integrity. It does not complete authorization.

Do not confuse CORS, origin checking, or an unguessable site ID with authentication. CORS constrains cooperating browsers; non-browser clients can forge headers. The reserved ingest_keys table exists so a future design can add hashed, revocable credentials without embedding the admin token in the SDK.
09 · Operations

Migrate, project, retain, observe, and shut down deliberately.

Versioned migrations

Embedded numbered SQL files run transactionally and record in schema_migrations. Never edit a released migration; append a new one and test fresh plus upgrade paths.

Legacy upgrade

Pre-v2 events is renamed, v2 tables are created, sites/domains inferred, URLs sanitized, timestamps copied, then the temporary table is dropped in one transaction.

Retention

Per-site retention_days runs at startup and every 24 hours. It deletes expired raw/daily data and rebuilds sessions crossing the cutoff.

Lifecycle

The server drains projections at startup, serves status at /api/status and /healthz, and uses signal-driven graceful shutdown.

# inspect durability and freshness
curl http://localhost:8080/api/status

# explicit maintenance, using the same DB_PATH
iris-server rebuild-projections
iris-server apply-retention

Signals that matter

Backups and restore drills; raw sequence and projection checkpoint; DB and WAL size; ingestion latency; busy/locked errors; retention duration and rows deleted. A SQLite-aware backup must preserve a consistent database/WAL state.

Known maintenance limit: retention does not yet batch large deletes, checkpoint WAL, reclaim file space, or report granular progress. Add those before delete volume can hold the single writer for a material period.
10 · Evolution

Move to ClickHouse when measurements demand it—not when the table feels large.

Stay on SQLite when…

A single node is acceptable, the serialized writer sustains peaks, projection lag remains bounded, indexed/projection reads meet goals, and retention is operationally cheap.

Split storage when…

You need concurrent ingestion replicas, sustained writes exceed one writer after batching, long-range segmentation misses targets, event volume reaches hundreds of millions, or retention/compression dominates operations.

The likely split keeps relational control-plane data in SQLite or PostgreSQL and sends event facts/analytical models to ClickHouse. Because v2 already treats raw events as a logical stream and projections as consumers, that migration need not change the browser event contract.

Architecture heuristic: optimize the seam before replacing the engine. Stable event IDs, explicit schema versions, projection checkpoints, immutable facts, and registered sites retain value under every future store.
11 · SDK release

The timezone and identity changes are a minor SDK release.

The shipped SDK gains an optional public timezone configuration and changes visitor/session behavior to the v2 contract. The repository uses Changesets and npm Trusted Publishing; normal releases never run npm publish from a developer machine.

  1. Add a minor changeset to this SDK PR and verify the build/package.
  2. Merge the implementation PR into main.
  3. The Release SDK workflow creates or updates chore: release packages, consuming changesets and updating the package version/changelog.
  4. Review and merge that release PR, then approve the npm-production environment deployment.
  5. GitHub OIDC publishes to npm and creates the matching tag/release; verify latest and package integrity.

12 · Retrieval practice

Answer first. Reveal second.

1. What exact event state does a 202 response guarantee?
The raw-event transaction committed, or the same event ID was already present. It does not guarantee zero projection lag or a refreshed dashboard.
2. Why must checkpoint advancement share the projection transaction?
If it advanced separately, a crash could mark uncommitted work complete or replay already-committed increments. One transaction makes the batch restartable without gaps or double counts.
3. Which identifier orders projection work, and which deduplicates delivery?
seq provides database order; client-generated id is the unique idempotency key.
4. Why is site timezone immutable after the first event?
It determines stored local_day, visitor rotation, and daily projections. Changing it would mix incompatible historical and future calendar semantics.
5. Are sessions still tab-lifetime IDs?
No. They are site-scoped, shared across same-origin tabs through localStorage, and roll after 30 minutes without tracked activity.
6. Can a forged Origin header bypass ingestion authentication?
There is currently no ingestion authentication to bypass. Hostname validation improves data integrity but does not prove the sender; a non-browser client can forge headers and payloads.
7. Which data may be safely deleted and regenerated?
Sessions, daily aggregates/distinct sets, and projection checkpoints. The retained raw events log is the rebuild source.
8. What happens when a duplicate event ID is retried?
The insert conflicts and does nothing; the request remains accepted without creating another raw row.
9. Why are URL query strings removed?
They frequently contain tokens, search text, email addresses, and campaign details. Removing query/fragment minimizes privacy leakage and reduces high-cardinality dimensions.
10. When does ClickHouse become justified?
When measured write throughput, multi-replica requirements, analytical latency, hundreds-of-millions scale, retention cost, or unbounded projection lag exceed the single-node SQLite envelope after reasonable tuning.
